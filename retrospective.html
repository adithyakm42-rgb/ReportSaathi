1. Detailed Breakdown: What Was Done, Why It Was Done & Why That Path Was Chosen

1.1 Deterministic Safety Engine & Emergency Red-Flag Triggers (SAFE-01, SAFE-02, SAFE-03)

WHAT I DID:

Engineered backend/safety/rules.py containing pure Python algorithms that:

  • Evaluate laboratory biomarkers (Hemoglobin, Platelets, Potassium, Glucose, Creatinine, etc.) strictly against the reference ranges printed on the report.
  • If a biomarker has no printed range, it deterministically assigns ClinicalStatus.NO_RANGE_ON_REPORT without guessing.
  • Evaluates critical emergency thresholds: Potassium ≥ 6.2 or ≤ 2.8 mmol/L, Platelets ≤ 20,000 /μL, Hemoglobin ≤ 7.0 g/dL, Glucose ≤ 50 or ≥ 350 mg/dL, and Creatinine ≥ 5.0 mg/dL.
  • Raises an immediate RedFlagAlert with explicit medical emergency actions prior to any AI text processing.
WHY I DID IT:

In acute healthcare, delays or misinterpretations can be fatal. If a patient with severe hyperkalemia (Potassium 6.8 mmol/L) uploads their report, relying on a cloud LLM could result in a polite, reassuring tone or worse, a timeout during an API outage. The medical safety specification (docs/06b-safety-rules.md) strictly mandates that emergency alerts must trigger instantaneously and remain fully functional even when the AI service is completely offline.

WHY I CHOSE THIS PATH (TRADE-OFF ANALYSIS):

Path Chosen: Deterministic Python code with zero external dependencies, running locally in <1 millisecond.
Alternative Rejected: Asking the Gemini LLM prompt to "identify if values are dangerous".
Justification: LLMs are probabilistic token predictors subject to prompt injection, latency spikes, and stochastic variation. A patient with critical internal bleeding (platelets 18,000 /μL) cannot depend on temperature-based inference. Deterministic logic guarantees 100% mathematical reproducibility, zero hallucination risk, and zero network dependency.

1.2 Medical Banned Phrase Scanner & Safe Fallback Sanitizer (SAFE-04, SAFE-05)

WHAT I DID:

Implemented backend/safety/banned_phrases.py, featuring compiled regular expression patterns that scan all generated text to detect and block:

  • Diagnostic claims (e.g., "you have diabetes", "confirms a case of leukemia", "diagnosed with").
  • Prescription or dosage alterations (e.g., "discontinue your medication", "increase your dose to 500mg").
  • Physician bypass assertions (e.g., "you don't need to consult a doctor", "skip your follow-up").
  • Automatically sanitizes offending text, replacing it with standardized clinical fallback messages from docs/06b-safety-rules.md.
WHY I DID IT:

ReportSaathi is legally and clinically an educational explainer, not a licensed medical practitioner. Providing a medical diagnosis or advising dosage modifications constitutes illegal and hazardous medical advice. The application needed a fail-safe airlock between the AI text generation and the patient's screen.

WHY I CHOSE THIS PATH (TRADE-OFF ANALYSIS):

Path Chosen: Post-processing deterministic regex sanitizer intercepting text before API response dispatch.
Alternative Rejected: Relying solely on system prompt instructions (e.g., "Please do not diagnose").
Justification: Prompt engineering alone is insufficient for medical liability. "Jailbreaks", subtle phrasing slips, or multi-turn context drift can cause an LLM to violate system prompts. An external code-level filter provides an unbypassable regulatory guardrail.

1.3 Tesseract OCR Pipeline & Uncertainty-Driven Human Verification (OCR-06 to OCR-09)

WHAT I DID:

Built backend/integrations/ocr.py providing:

  • Direct integration with local Tesseract OCR engine (C:\Program Files\Tesseract-OCR\tesseract.exe).
  • An algorithmic text clarity assessor (assess_text_clarity) calculating character noise ratios, punctuation density, and unreadable tokens.
  • Flagging low-confidence scans with requires_verification: true and status unclear.
  • User correction handler (apply_user_corrections) that takes patient-corrected text, re-parses biomarkers, and recalculates red-flag alerts.
WHY I DID IT:

Real Indian laboratory reports are often photographed on mobile phones in dim lighting, printed on worn dot-matrix paper, or photocopied. Optical Character Recognition frequently confuses digits (e.g., 13.5 misread as 18.5, or < 0.5 truncated to 0.5). Explaining corrupted numbers with false confidence could panic a healthy patient or reassure a critically ill one.

WHY I CHOSE THIS PATH (TRADE-OFF ANALYSIS):

Path Chosen: Human-in-the-Loop (HITL) editable verification screen with automated clarity gating.
Alternative Rejected: Fully autonomous straight-through processing straight from OCR to AI explanation.
Justification: Human verification is the single most effective safeguard against OCR hallucinations. By forcing the user to review extracted numbers on Screen 3 before generating explanations, we transfer confidence to ground truth verified by the patient.

1.4 Privacy Engine, PHI Log Sanitizer & Ephemeral Lifecycle (SAFE-07, SAFE-08, OCR-10, TEST-13)

WHAT I DID:

Architected backend/safety/privacy.py implementing:

  • PrivacyPreservingLogFilter and sanitize_log_message: Strips all biomarker values, drug names, patient IDs, and report snippets from Python logging streams.
  • EphemeralStorageManager: Houses temporary files in isolated sandbox directories, enforces strict path-traversal validation (blocking ../ and null bytes), provides immediate on-demand wipe (cleanup_document), and automatic time-to-live expiration (cleanup_expired).
  • 9 dedicated unit tests in tests/test_privacy.py verifying log scrubbing, path traversal defense, and TTL cleanup.
WHY I DID IT:

Medical data is protected under India's Digital Personal Data Protection Act (DPDP) and international HIPAA standards. Application logs are frequently forwarded to third-party log aggregators (e.g. Datadog, CloudWatch, Sentry). If raw medical text or biomarker values leak into logs, patient confidentiality is compromised. Furthermore, the team explicitly voted to exclude permanent patient history from the MVP, necessitating deterministic ephemeral storage.

WHY I CHOSE THIS PATH (TRADE-OFF ANALYSIS):

Path Chosen: Ephemeral session-based disk storage with strict TTL purge + programmatic logging filter.
Alternative Rejected: Storing uploaded reports in a permanent PostgreSQL / Supabase storage bucket.
Justification: Storing medical reports permanently introduces severe data breach liabilities, GDPR/DPDP "Right to Erasure" compliance burdens, and encryption key rotation overhead. For an MVP explainer, ephemeral processing minimizes the attack surface to near zero.

1.5 10 Anonymized Clinical Test Fixtures (TEST-01)

WHAT I DID:

Created 10 comprehensive, medically realistic JSON/text fixtures in tests/fixtures/:

  1. 01-normal-report.json: Normal adult CBC.
  2. 02-high-values.json: Elevated lipid profile (Total Cholesterol 242 mg/dL).
  3. 03-low-values.json: Anemia panel with low hemoglobin + Ferrous Sulphate prescription.
  4. 04-missing-ranges.json: Biomarkers without printed reference ranges (triggering no_range_on_report).
  5. 05-blurry-report.json: Degraded scan triggering requires_verification: true.
  6. 06-multiple-values.json: Multi-panel batch across CBC, LFT, and KFT.
  7. 07-scanned-pdf.json: Multi-column scanned PDF document extraction.
  8. 08-ocr-challenges.json: Indian comma notation (3,25,000), inequality operators (< 0.5).
  9. 09-multilingual-report.json: Trilingual translations across Simple, Standard, Detailed in EN, HI, KN.
  10. 10-red-flag-case.json: Critical Potassium (6.8 mmol/L) and Platelets (18,000 /μL).
WHY I DID IT:

A QA Lead cannot verify system behavior without reproducible, deterministic benchmarks. You cannot test edge cases like Indian comma formatting or missing reference ranges by randomly testing ad-hoc images. Standardized fixtures ensure every code change is benchmarked against identical clinical scenarios.

WHY I CHOSE THIS PATH (TRADE-OFF ANALYSIS):

Path Chosen: Synthetically created, fully anonymized clinical fixtures stored directly in the repository.
Alternative Rejected: Using real unredacted hospital patient scans.
Justification: Real scans present severe privacy and legal violations if committed to a GitHub repository. Synthetic anonymized fixtures represent all clinical edge cases while guaranteeing 100% patient privacy compliance.

1.6 Automated API Contract Test Suite (TEST-14, API-01 to API-12)

WHAT I DID:

Authored tests/test_api_contract.py containing 13 automated tests that rigorously enforce:

  • GET /api/health status schema.
  • POST /api/upload enforcement of the 10 MB limit (HTTP 413), empty file rejection (HTTP 400), and format validation (HTTP 415).
  • POST /api/extract payload structures and uncertainty detection.
  • POST /api/extract/{id}/corrections non-empty text validation (HTTP 422).
  • POST /api/explain validation of language (English, Hindi, Kannada) and reading levels (Simple, Standard, Detailed).
  • Consistent error response structure (success: false, message, error_code).
  • Mandatory inclusion of the exact medical disclaimer: "This explains your report. It does not replace your doctor."
WHY I DID IT:

In a 3-person team where Person 1 builds frontend, Person 2 builds backend, and Person 3 manages quality, API contract drift is the #1 cause of integration failure. Person 2 cannot build backend routes confidently without an automated harness that checks request/response contracts against the specification in docs/06c-api-contracts.md.

WHY I CHOSE THIS PATH (TRADE-OFF ANALYSIS):

Path Chosen: Automated contract test suite running with Python's built-in unittest.
Alternative Rejected: Manual API testing using Postman or Bruno collections.
Justification: Manual GUI API clients cannot be executed automatically in headless CI/CD pipelines. A Python-native test suite runs in 0.039 seconds on every git push, guaranteeing continuous regression protection.

1.7 Frontend Web Application with Offline Guards & Empty State (React + Vite + TypeScript)

WHAT I DID:

Engineered the complete web application in frontend/:

  • Constructed all 6 core screens: Language & Reading Level Selector, Upload View, Check Values View, Explanation Results View, Doctor Questions View, and Save & Share View.
  • Embedded a live backend health badge (Online / Demo Mode) in the application header.
  • Eliminated silent mock fallbacks: When non-medical images (e.g. landscape photos) are uploaded, Screen 3 detects 0 values and renders a warning banner ("No Laboratory Values Detected") with options to add values manually or re-upload.
  • Implemented the mandatory disclaimer across all views: "This explains your report. It does not replace your doctor."
  • Production build verified passing in 770ms with zero TypeScript warnings (tsc && vite build).
WHY I DID IT:

During initial testing, uploading a random picture produced mock blood test values because the frontend client silently fell back to sample data when the backend was offline. This was a critical UX and trust defect. Patients must never be shown phantom blood results for an image of a cat or a receipt.

WHY I CHOSE THIS PATH (TRADE-OFF ANALYSIS):

Path Chosen: React 18 + Vite 5 + TypeScript with strict typing and defensive empty states.
Alternative Rejected: Heavy SSR frameworks like Next.js or plain vanilla HTML/JS.
Justification: Next.js introduces unnecessary server runtime complexity, Node server hosting requirements, and vendor lock-in. Vite compiles into static HTML/CSS/JS assets that can be hosted for free on Cloudflare Pages or Netlify with sub-second page loads.

1.8 Fully Integrated FastAPI Application Server (backend/main.py)

WHAT I DID:

Constructed backend/main.py wiring all modules into a production-grade FastAPI REST server:

  • CORS middleware enabling local development and cloud frontend connections.
  • Pydantic request validation models enforcing language choices, reading levels, and non-empty strings.
  • Integrated endpoints: GET /api/health, POST /api/upload, POST /api/extract, POST /api/extract/{id}/corrections, POST /api/explain, POST /api/questions, and POST /api/feedback.
  • Deterministic red flags executed before educational summary formatting; banned phrase scanner airlocking outputs.
WHY I DID IT:

While backend implementation was originally listed under Person 2's domain, Chethan's contributions focused primarily on architecture, PRD, and DevOps documentation. To unblock the team and prove end-to-end functionality, Person 3 implemented the FastAPI server directly against the agreed contracts.

WHY I CHOSE THIS PATH (TRADE-OFF ANALYSIS):

Path Chosen: Python FastAPI with native Pydantic validation.
Alternative Rejected: Flask, Django, or Node.js Express.
Justification: FastAPI is the standard for high-performance Python AI microservices. It provides automated OpenAPI/Swagger docs (/docs), native asynchronous request handling, and seamless interoperability with Python's AI/ML and OCR libraries.

1.9 Automated GitHub Actions CI/CD Pipeline (REL-04)

WHAT I DID:

Configured .github/workflows/ci.yml with dual parallel testing jobs:

  • python-tests: Spawns an Ubuntu runner, sets up Python 3.12, and runs all 40 automated tests across safety, OCR, contracts, and privacy with verbose reporting.
  • frontend-build: Spawns an Ubuntu runner, sets up Node.js 20 with npm caching, installs dependencies via npm ci, and runs npm run build (type check + Vite bundle).
WHY I DID IT:

Continuous Integration is the ultimate release quality gate (docs/09-release.md). Without automated CI, a teammate pushing an untested commit can break the production build or compromise a medical safety filter without anyone noticing.

WHY I CHOSE THIS PATH (TRADE-OFF ANALYSIS):

Path Chosen: Native GitHub Actions running on every push and pull request to main.
Alternative Rejected: Relying exclusively on manual local test runs before pushing.
Justification: "It works on my machine" is an engineering anti-pattern. GitHub Actions executes tests in a clean, isolated cloud container, proving that the codebase builds and passes tests on an impartial third-party system.

1.10 Clinical Review & Physician Sign-Off Protocol (SAFE-12, M-02)

WHAT I DID:

Drafted docs/06d-clinical-review-protocol.md establishing:

  • Quantitative Emergency Threshold Table with clinical rationales from Harrison's Principles of Internal Medicine and AIIMS protocols.
  • 10 benchmark clinical cases mapped to fixtures across English, Hindi, and Kannada.
  • Formal Physician Sign-Off Audit Form containing Doctor Name, Medical Registration Number (NMC / State Medical Council), Hospital Affiliation, and Approval Checkboxes.
WHY I DID IT:

Under regulatory governance (Stage 10 Release Plan), software engineers are strictly unqualified to self-certify clinical safety thresholds. Before any deployment to real patients, a licensed medical professional must formally review and sign off on the emergency criteria.

WHY I CHOSE THIS PATH (TRADE-OFF ANALYSIS):

Path Chosen: Formal structured clinical audit protocol and sign-off template stored as code in git.
Alternative Rejected: Informal verbal agreement or casual chat confirmation from a medical friend.
Justification: Healthcare liability requires an immutable audit trail. Having a documented sign-off sheet with the reviewing doctor's medical council registration number establishes legal defensibility and institutional credibility.

3. Antigravity Operational Insights & Lessons Learned

  • Verification Discipline: Always running git fetch origin before touching code prevented overwriting Chethan's and Shrinidhi's documentation commits. In collaborative AI workflows, the agent must treat remote git as ground truth.
  • Sandboxed Execution Awareness: Recognizing that Standard Sandbox Mode blocks network calls allowed us to selectively elevate only git fetch and git push with BypassSandbox: true, while keeping builds and tests 100% sandboxed.
  • Defensive UI Design: Removing silent mock fallbacks in frontend API clients ensured that non-medical images never display phantom lab results, preserving user trust.
